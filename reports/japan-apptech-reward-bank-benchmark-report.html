1. 결론

검증 결과일본 계좌이체/은행송금은 은행명만으로 부족하고 은행명 또는 금융기관코드 + 지점명 또는 지점코드를 함께 받는 구조가 맞음.
선택 UI금융기관과 지점 수가 많아 드롭다운 전체 나열은 피하고, 검색 우선 + 최근/추천 은행 최대 3개 + 지점 검색 방식이 적합.
계좌 유형일본 송금 폼은 普通預金(일반/보통예금), 当座預金(당좌/수표성 계좌), 貯蓄預金(저축예금)을 다루지만 앱테크 출금은 普通預金(일반/보통예금)을 기본값으로 두는 것이 현실적.
서비스 판단은행송금은 가능하지만 본인명의 계좌, 명의カナ(계좌명의 가나 표기), ゆうちょ銀行(우체국은행) 예외, 계좌오류/반려 CS가 있어 MVP는 포인트/기프트 교환 우선이 안전.
핵심 결론: 일본에서 은행송금을 제공하려면 은행명과 지점명/지점코드를 같이 선택받는 형태가 맞다. 계좌유형은 화면에 명확히 표시하되 기본은 普通預金(일반/보통예금)으로 두고, 当座預金(당좌/수표성 계좌), 貯蓄預金(저축예금)은 필요 시 선택 옵션으로 제공하는 것이 좋다. 다만 초기 앱테크 리워드는 은행송금보다 PayPay/Amazonギフト(Amazon 기프트)/주요 포인트 교환을 먼저 제공하는 사례가 더 많다.
조사 근거: Zengin-Net 통계는 2026년 3월 기준 금융기관 1,086개, 지점 29,010개를 집계하고 있으며, 예를 들어 みずほ銀行(미즈호은행)도 400개 이상 지점이 확인된다. 따라서 정적 목록보다 은행/지점 검색 API 또는 송금대행사의 금융기관 마스터를 붙이는 설계가 필요하다.

3. 리워드 관련 화면

Cashwalk JP

기프트 중심은행입력 없음

일본판 Cashwalk는 현금 송금 화면이 아니라 기프트카드/타사 포인트 코드 교환 흐름이 핵심이다. App Store 설명 기준 현금 환전은 비대응이며, 교환 탭에서 편의점·카페 바코드형 기프트, Amazonギフト(Amazon 기프트), dポイント(d포인트), Pontaポイント(Ponta 포인트) 같은 교환처를 제공한다.

걷기 -> 100보마다 코인BOX -> 탭해서 코인 수령 -> 交換(교환) 탭 -> 기프트/포인트 선택 -> 코드/URL 발급 -> Myギフトカード(My기프트카드)에서 확인

Moneywalk JP

DotMoney외부 경유

Moneywalk는 앱 화면에서 Cash & Gift cards 교환을 전면에 둔다. 은행송금은 앱이 계좌를 직접 받기보다 DotMoney 경유 구조이며, DotMoney 도움말에서 Shop → 포인트/특전 교환 → ID 연동 흐름이 확인된다.

Shop -> ポイントと特典を交換(포인트와 특전 교환) -> 포인트 선택 -> DotMoney 연동 -> 본인확인 -> 외부 교환처 지급

クラシルリワード

선택형 특전PayPay/Amazon/포인트

PayPay, Amazonギフト(Amazon 기프트), dポイント(d포인트), Ponta, 楽天ポイント(라쿠텐 포인트), Vポイント(V포인트), 쿠폰형 상품이 함께 보인다. PayPay Money Light 출금 불가 안내도 포함된다.

코인 적립 -> コイン交換(코인 교환) -> 교환처 선택 -> 로그인/회원가입 -> 교환 신청 -> 각 교환처 지급

Powl

PayPay 연동Money Light

Powl 포인트를 PayPay 잔액으로 충전하는 공식 연동 사례. 일본에서는 PayPay 사용처가 넓어 현금보다 체감 가치가 빠르다.

Powl 포인트 -> 交換する(교환하기) -> PayPay残高(PayPay 잔액) 선택 -> 교환 신청 -> PayPay Money Light 지급

TikTok Lite

대형 성공 앱PayPay/えらべるPay

동영상 시청으로 포인트를 모아 PayPayポイント(PayPay 포인트) 등으로 교환하는 구조. 리워드 UX가 앱 체류와 결합된 사례다.

영상 시청/체크인 -> 포인트 적립 -> ギフト/交換(기프트/교환) -> PayPay 또는 えらべるPay(선택형 Pay) -> 지급

ハピタス

직접 은행송금수수료/완료일 안내

現金（直接口座振込, 현금/직접 계좌입금） 상품이 있고, 최소 교환 포인트·수수료·완료일이 표로 안내된다. 로그인 뒤 계좌 등록으로 이어진다.

현금 교환 -> 조건 확인 -> 로그인 -> 은행/지점/계좌 입력 -> 포인트 입력 -> 인증 -> 은행 입금

ポイントタウン

은행별 교환계좌 정책 필요

은행별 현금 교환 페이지를 제공한다. 본인명의, 1계좌 제한, 계좌 변경 제한 같은 정책이 UI/약관에 필요하다.

ポイント交換(포인트 교환) -> 은행 선택 -> 로그인 -> 계좌정보 등록/확인 -> 교환 신청 -> 입금 상태 안내

GMOポイ活

은행/지점 검색직접 계좌입력

공개 도움말에서 주요 은행 버튼, 기타 은행 검색, 支店名(지점명) 검색 흐름을 안내한다. 실제 입력 폼은 로그인 뒤 화면이다.

現金(현금) 선택 -> 주요 은행/검색 -> 금융기관 선택 -> 支店名(지점명) 검색 -> 계좌명/명의カナ(명의 가나)/포인트 입력 -> 신청

6. 한국과 다른 점

항목한국 앱테크 관성일본 포이활/앱테크 관성설계 시사점
리워드 체감현금, 네이버페이, 카카오페이, 모바일상품권이 직관적PayPay, Amazonギフト(Amazon 기프트), dポイント(d포인트), Ponta, 楽天ポイント(라쿠텐 포인트), Vポイント(V포인트) 등 생활권 포인트 체감이 큼1차 MVP는 현금보다 즉시 쓸 수 있는 교환처를 앞에 배치
교환처 구조앱이 직접 쿠폰/상품권을 지급하거나 국내 포인트로 전환DotMoney, デジコ, giftee Box, えらべるPay 같은 중간 교환 플랫폼 경유가 많음직접 제휴보다 플랫폼 제휴로 교환처를 빠르게 넓히는 전략 유리

8. 운영/제휴 체크

질문답변설계 반영
은행이 많아 선택이 어렵지 않나?맞다. 금융기관 수가 많아 전체 목록이나 많은 은행 버튼을 보여주면 부담이 크다. 기본은 은행명 검색으로 두고, 보조로 최근 선택/추천 은행을 최대 3개 정도만 노출하는 편이 낫다.검색 우선, 최근/추천 은행 최소 노출, 금융기관코드는 자동 저장
PayPal인가?목업의 은행 버튼은 PayPal이 아니라 `PayPay銀行(PayPay은행)`이다. PayPay는 일본 간편결제/포인트 생태계, PayPay銀行(PayPay은행)은 은행이다. PayPal은 별도 글로벌 결제 서비스다.은행 버튼은 `PayPay銀行(PayPay은행)`로 표기
계좌종류가 필요한가?필요하다. 일본 송금은 `普通預金(일반/보통예금)`, `当座預金(당좌/수표성 계좌)` 등 계좌종류/預金種目(예금종목)을 요구하는 경우가 있다. 포인트사이트는 보통 普通預金(일반/보통예금)만 허용하기도 한다.계좌종류 필드 노출, 기본값은 普通預金(일반/보통예금)
수수료가 있나?있을 수 있다. ハピタス처럼 직접 계좌입금에 교환 수수료를 명시하는 사례가 있고, 은행/교환처/대행사별로 다르다.교환 전 수수료와 완료 예정일을 확인 화면에 표시
본인확인은 어떻게 하나?서비스 로그인, SMS/메일 인증, 비밀번호/2FA, 외부 교환 플랫폼의 본인확인, 계좌명의カナ(계좌명의 가나)와 회원명 비교를 조합한다. PayPay 은행계좌 등록은 사전 本人確認(본인확인)이 필요하다고 안내한다.교환 신청 전 인증 단계와 명의 불일치 오류 처리 필요
계좌 인증은 어떻게 하나?은행/지점코드 유효성, 계좌번호 자리수, 명의カナ(명의 가나) 형식, 계좌체크 API/송금대행사 검증, 실제 송금 결과를 단계적으로 확인한다. 모든 은행에서 실시간 명의조회가 되는 전제로 보면 위험하다.검증 실패/송금 실패/반려 상태를 별도 상태값으로 운영
기프트 제휴는 어떻게 하나?개별 브랜드와 직접 계약하거나, デジコ/giftee Box/えらべるPay/DotMoney 같은 교환 플랫폼을 붙인다. MVP는 개별 제휴보다 플랫폼 연동이 빠르다.1차는 디지털기프트/교환 플랫폼 계약 우선
은행송금도 제휴가 필요한가?직접 은행별 제휴를 맺기보다 송금대행/결제대행/은행 API/자금이동업자 구조를 검토하는 게 일반적이다. 자체 송금은 정산, AML, 계좌오류 CS 부담이 크다.은행송금은 대행 솔루션 또는 DotMoney 경유를 우선 검토
